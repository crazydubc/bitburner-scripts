# Go assessment and first implementation

Keep the existing opponent strategies for now. The first production change fixes runtime/game-state defects and secures an already-winning two-pass finish. An exact tactical evaluator was built and checked against the official engine, but its larger match sample did **not** improve aggregate win rate. That experiment is recorded here and excluded from `go.js`.

## Production changes

| Finding | Effect | Change |
| --- | --- | --- |
| Pattern handlers call undefined global `sprintf` | A matching defense/disruption pattern throws and enters the ten-second recovery loop. | Use template strings; execute both matching paths in the checks. |
| Opponent strategy is selected once outside the game loop | After a reset picks another faction, the bot continues using the previous faction's strategy. | Read the current opponent during each turn. |
| Legal-move cache is keyed only by a reused turn number | A retry/new game can reuse moves from a different board. | Invalidate after each fresh board/analysis snapshot and on reset; check legality before submitting. |
| Two cheat target scans stop at `size - 1` | Targets confined to the last row/column are ignored. | Scan the entire board. |
| Wall-breaking uses 70% despite a configured 90% threshold; extra SF4 restriction; legacy `cheats` flag ignored | Unexpected risk or unavailable actions despite valid Go cheat access. | Honor the configured threshold and both disable controls; require the existing SF14 eligibility, without unrelated SF4 gating. |
| Bot continues after an opponent pass while ahead | Further play can jeopardize an already-secured win and delay the next game. | Check the engine score and pass to finish when Black is ahead. Continue playing when behind. |

The last change favors securing wins and moving to the next game. It can finish with fewer controlled nodes than playing the board out, so it is not a proven improvement to bonus power per hour. Real game timing and node-power gain should be measured separately from win percentage.

No new runtime dependency, cheating capability, opponent selection policy, or batcher change is introduced. Existing move priority and heuristic estimates remain in production.

## Tactical experiment: accurate arithmetic was not enough

The original surrounding-liberty estimator sums neighboring chains' liberty counts, so a chain touching several sides and liberties shared between groups can be counted repeatedly. Capture/defense rankings similarly overcount some chains. Several heuristic thresholds were effectively tuned around these estimates.

The experiment built each distinct chain once per board, calculated actual post-move liberties/captures, ranked captures and atari rescues by distinct stones, rejected simple self-atari, and used an unbiased shuffle. Its model matched the pinned engine on **3,754** move/liberty/capture/chain-size comparisons, including edges, offline nodes, captures, and positions generated by legal play.

Nevertheless, combining those mathematically correct changes with the existing strategy did not produce a reliable win-rate improvement. In particular, stronger self-atari filtering can reject intentional sacrifices, and changing the urgent-move priority can trade one opponent's wins for another's. Retuning the policy or adding bounded reply search is separate work; do not equate an exact local liberty count with a stronger overall Go player.

## Reproduce

Use Node 24 and an external checkout of `bitburner-official/bitburner-src` at `1da7316ffd9d281b45a86c4c54ec532276557892` (3.0.1). No game or save is needed. From this scripts repository:

```sh
node audit/2026-10-17-speedrun/checks/go-lifecycle.mjs
node audit/2026-10-17-speedrun/checks/go-tactics-checks.mjs /path/to/bitburner-src
node audit/2026-10-17-speedrun/checks/go-benchmark.mjs /path/to/bitburner-src 13 2 317
node audit/2026-10-17-speedrun/checks/go-benchmark.mjs /path/to/bitburner-src 13 6 2048 experiment
```

The experiment command applies [go-tactics-experiment.patch](go-tactics-experiment.patch) inside a temporary directory; it never patches the working checkout. The experimental model and all verification files remain under `audit/`, preserving main's removal of the old test directory. `.mjs`, `.patch`, `.json`, and `.md` files are outside the downloader's normal script extensions.

## Next work with the best chance of improving win ratio

### User-reported game baseline — 2026-10-17

Interpreting the supplied records as wins / games played:

| Opponent | Wins / games | Win rate |
| --- | --- | --- |
| Netburners | 8 / 8 | 100% |
| Daedalus | 6 / 6 | 100% |
| Illuminati | 2 / 5 | 40% |
| Slum Snakes | 3 / 3 | 100% |
| Tetrads | 4 / 5 | 80% |
| The Black Hand | 3 / 3 | 100% |
| **Total** | **26 / 30** | **86.7%** |

Illuminati accounts for three of the four losses. This makes it the first opponent to investigate with paired tests, while retaining checks against the other five opponents. No strategy was changed in response to this small sample. The board size, cheat settings, SF inventory, exact loaded script revision and match durations were not supplied, so these observations cannot establish a before/after improvement or be pooled with the offline samples above. The user is testing the combined branch, but the exact running code was not inspected.

### Further experiments

1. **Measure per opponent.** Record before/after wins and losses from the Go statistics screen, keeping board size, cheat settings, SF state, and faction mix comparable. Aggregate wins alone can hide a regression against Illuminati or Tetrads. Do not improve the displayed ratio merely by choosing easier factions and forfeiting the desired bonuses.
2. **Evaluate one strategy change at a time.** Keep a held-out seed set. Separate exact liberties, rescue priority, sacrifice handling, and tie-breaking; the combined experiment cannot identify which change caused an individual loss.
3. **Add bounded tactical reply analysis.** Candidate moves should be compared against an opponent's immediate capture/escape response, particularly before joining a large weak group or rejecting a sacrifice. Cap analysis work and measure any delay added to live games.
4. **Make cheat risk aware of the score.** A uniform success threshold ignores the cost of jeopardizing a nearly certain win. Validate the expected value of a cheat against the no-cheat continuation, including ejection probability and remaining moves.
5. **Optimize bonuses per elapsed hour alongside wins.** Finishing winning games early can trade score for game throughput; the offline adapter deliberately removes timing delays, so it cannot settle that tradeoff.
