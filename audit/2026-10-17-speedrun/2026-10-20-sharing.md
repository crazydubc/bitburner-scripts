# Faction-aware sharing with spare RAM

The old kernel shared spare RAM without checking for faction work. It required more than 1,200 GB of network RAM, waited roughly forty-one seconds after startup before the first eligible pass, divided available RAM by 6 even though the worker cost 4 GB, skipped home, and let Stanek consume spare RAM first. Each worker shared once for ten seconds, with launches at least eleven seconds apart. Outstanding workers could also reduce the RAM seen by the next batch planner.

The updated kernel enables sharing in BN1 before SF4, where manual faction work cannot be detected. In BN4 or with SF4, it follows player and sleeve faction work. It fills usable spare RAM within explicit buffers and keeps workers alive across batch boundaries. The planner counts their RAM as reclaimable; the dispatcher stops only handed-off workers whose RAM is needed for a hacking launch. Batch formulas, requested H/G/W delays, target selection and the cash reserve are unchanged. Sharing uses preemptible spare capacity, not a fixed deduction from the batcher's RAM budget.

**2026-10-21 follow-up:** the original manual BN1 toggle was unnecessarily conservative. Default `share-mode: auto` now uses the kernel's existing BitNode/source-file snapshot to enable BN1 sharing without a new helper or RAM increase. This applies to BN1.1 and repeat BN1 runs before SF4. Explicit `on`/`off` overrides remain authoritative; no saved configuration is overwritten.

**2026-10-22 buffer correction:** the percentage cushion previously used total installed RAM. A 4,096 GB home reserved 204.8 GB for sharing, so the reported 97 GB free produced zero threads. The roughly $31.72b next home upgrade matches that capacity in BN4. The cushion now uses available RAM before our own sharing allocation (free RAM plus RAM held by our tracked share workers). In that scenario the fixed 64 GB floor applies: eight 4.1 GB threads fit, leaving 64.2 GB free. Counting owned sharing back into the pool keeps the percentage stable between sweeps. The percentage no longer causes intermittent sharing solely because most installed RAM is busy hacking.

**2026-10-22 continuity correction:** after the buffer fix, the user still observed roughly ten seconds without sharing between active periods. The kernel stopped every worker at the end of a batch wait, then performed target selection, calculations, a RAM census and dispatch before sharing resumed. Persistent workers now survive those phases. The home dispatcher receives a JSON string containing the owning kernel PID and its share PIDs, verifies the live script identity/owner and actual RAM, and reclaims only a host blocking its next launch. Unused workers keep their PIDs. Both main-target and botnet dispatches use this handoff; allocation resumes immediately afterward, including when the last hacking PID has already ended. A forced sweep when the batch finishes also fills newly released RAM before target calculations, even if the batch left zero workers and the normal two-second allocation interval has not elapsed. No new background manager or concurrent Netscript loop is introduced.

## What share improves

The official implementation applies share power to faction work. Hacking Contracts receives the full multiplier; Security Work and Field Work receive a partial benefit through their hacking-related terms. The same reputation formulas are used by sleeves. Company work, crimes, faction donations, corporation bribes, infiltration rewards and passive faction reputation are not boosted by share.

Share takes effect while its call is running, so it can help even when the kernel reclaims a worker before its ten-second cycle ends. Extra cores and intelligence increase effective sharing threads. The share multiplier is `1 + ln(1 + effectiveThreads) / 25`; returns diminish sharply:

| Effective threads | Hacking-faction-work multiplier |
| --- | --- |
| 10 | 1.096× |
| 100 | 1.185× |
| 1,000 | 1.276× |
| 10,000 | 1.368× |

These are formula examples, not measured speedrun gains. Moving scarce money-making RAM into sharing is not automatically worthwhile. The current policy uses residual capacity during batches and between them, yielding it when the next dispatch needs it. It does not claim an optimal income-versus-reputation allocation.

## Allocation and priority

- Default `--share-mode auto` enables spare-RAM sharing in BN1 before SF4 without polling unavailable player-work APIs. It stays enabled during crimes/company work too, since manual work cannot be detected; only faction work benefits. Elsewhere it checks current work at most once every five seconds. Player faction work or any sleeve faction-work task enables sharing. Unknown initial work never enables it. A failed helper read retains a previously valid snapshot until it is fifteen seconds old, then the next check disables sharing; a successful non-faction snapshot stops it immediately.
- Useful sharing takes priority over this kernel's Stanek charges. It kills only those tracked charge PIDs when a faction-work need appears. Otherwise Stanek retains its existing role.
- Each allocation sweep uses current used/max RAM and the worker's actual script RAM cost. It fills whole threads up to the buffer, checks again after asynchronous copying, and resizes workers as other scripts consume or release RAM. Sweeps normally run at most once every two seconds; dispatch and batch completion reset that throttle so newly available RAM can refill immediately.
- On **home**, leave the greater of **64 GB or 5% of available RAM** free. On other hosts, leave the greater of **8 GB or 5% of available RAM** free. Available RAM includes memory currently occupied by this controller's own share workers, so resizing does not repeatedly shrink the buffer. These are sharing buffers, not a global guarantee against other scripts consuming RAM. A later sweep reclaims sharing if another consumer enters that buffer.
- Home and rooted worker servers are eligible; high-core hosts are considered first. Hacknet servers remain excluded because script RAM consumption reduces hash production. Tiny hosts without room above the buffer are skipped. The old 1.2 TB network gate is gone, along with its redundant per-host max-RAM helper calls during each batch census.
- Managed workers repeat share calls without added sleeps and remain alive through target calculations and RAM censuses. The census adds their reclaimable RAM back into its budget. Before each H/G/W launch, the dispatcher reclaims only explicitly handed-off workers on a host that lacks enough genuinely free RAM. Manual/unrelated processes are excluded. The original fifteen dispatcher arguments retain their order; an optional sixteenth string carries the handoff, so old callers still work.
- Optional Stanek charges still stop at the end of the batch wait. An empty Stanek gift now keeps waiting for the batch instead of prematurely starting a new dispatch. Kernel errors/retries and normal exits stop all owned sharing.
- A kernel exit also stops its tracked sharing PIDs. A share worker checks its owner's PID between cycles; if owner cleanup fails, it exits after the current cycle, within approximately ten seconds of owner loss. Standalone `bin/share.js` still performs one cycle.
- The kernel log reports the reason sharing is active/idle, allocated threads/RAM and configured buffers. It reports mode changes and at most once per minute while active. A full batch may leave no share capacity; that is expected.

Where work detection is used, the work snapshot is a read-only home helper. Its allocation uses current effective API RAM costs, including SF4.1/SF4.2 costs, before any optional API read. Missing helpers, insufficient home RAM and unavailable APIs cannot enable sharing from an unknown state; repeated failures expire the short-lived cache. BN1 before SF4 needs no work helper. No task, faction, focus or purchase is changed.

## Upgrade and controls

Pull the same testing branch:

```text
home
run git-pull.js --branch testing/bn1-go-audit
```

After `Pull complete`, **restart both autopilot and kernel from the updated home copies**. Autopilot needs the new remote dependency list so it can copy `share-controller.js` before offloading kernel. Stop existing instances first, start `autopilot.js` from home, and let it relaunch kernel. No separate persistent sharing manager needs launching. Include `bin/share-context.js` in the pull; both new files are in the downloader fallback list.

For the continuity correction, pull **all** updated files, especially `kernel.js`, `utils.js`, `share-controller.js` and `bin/serverRun.js`. Restart kernel so the new controller and handoff are loaded together; autopilot can relaunch it from home. Leave `share-mode: auto`. Do not update just the worker: its existing continuous loop was not the batch-boundary problem.

In BN4 and subsequent runs with Singularity, the default follows faction work automatically, including a useful faction-reputation or donation-favor work goal. It stops allocating sharing when the player and sleeves leave faction work. It does not override the faction worker's progression decisions.

In BN1 before SF4, manual work cannot be read through the official API, so the default now enables sharing from spare RAM automatically. The BN1 panel and faction roadmap explain this behavior. There is no need to change modes when starting or stopping faction work. If you previously followed the manual BN1 instructions, return `kernel.js.config.txt` on home to:

```json
{
  "share-mode": "auto"
}
```

Restart kernel from the updated home copy to load this change; autopilot can relaunch it. Once entering BN4 or owning SF4, `auto` follows detected work without another config edit. Manual `on` deliberately enables sharing in any BN and bypasses work detection; `off` disables it even in BN1. Both preserve their meaning across BN transitions. In other BNs without SF4, use `on` for manual faction work if desired. Avoid a second kernel instance.

All sharing controls can be placed in the config or supplied as flags:

```json
{
  "share-mode": "auto",
  "share-home-buffer": 64,
  "share-host-buffer": 8,
  "share-buffer-fraction": 0.05
}
```

`share-mode` accepts `auto`, `on` and `off`. Buffer sizes are GB; the fraction is between zero and one and now applies to available capacity, including owned share workers, rather than installed RAM. Keep enough home RAM for RPC helpers, faction planning and Go snapshots. With the defaults, small home servers simply do not run share workers.

## Validation

The `share-allocation.mjs` suite executes the real controller, worker, work helper, RPC transport and kernel. It tests BN1 automatic mode before SF4 (including repeat runs and idle sleeves), explicit overrides, player/sleeve work eligibility in BN1/BN4/other BNs with SF4, company/crime/idle exclusion when detectable, field/security work, maximal whole-thread packing, fixed/percentage buffers, expansion/shrinking, unrelated PIDs, failed launches/copies, RAM changes and cancellation during copying, effective helper RAM, absent data, and owner loss. Its two-dispatch kernel fixtures use default `auto` in BN1 and BN4 and prove sharing survives into the second census without reducing the planned thread budget, on a network smaller than 1.2 TB.

The batch formula/invariant and upgrade-compatibility checks pass, including the earlier undefined-argument regression. Existing RPC/config deployment and BN1-guide checks pass. The pinned official RAM calculator reports these changes relative to before the sharing feature:

| Script | Before | After |
| --- | --- | --- |
| Kernel | 5.30 GB | 5.85 GB |
| Share worker | 4.00 GB | 4.10 GB |
| Temporary dispatcher | 4.00 GB | 4.90 GB |
| BN1 guide | 8 GB | 8 GB |
| Autopilot | 4.2 GB | 4.2 GB |

The kernel increase pays for exact-PID cleanup and a live RAM read; the worker increase pays for owner liveness. The optional context helper costs 2.1 GB for player work at effective SF4.3, 3.6 GB at SF4.2, or 9.6 GB at SF4.1. Reading sleeve tasks adds 8 GB. Sleeves alone cost 9.6 GB. There is no new permanently resident home helper.

The October 22 buffer correction reproduces the 4 TB / 97 GB case against the old buffer (zero threads), then passes with eight threads through three minutes of work polling. The continuity follow-up executes the real BN1/BN4 kernel through two dispatches with simulated ten-second calculator delays, both with spare capacity and with a fully occupied batch: unaffected workers retain their PIDs, the planner sees reclaimable capacity, and preempted hosts refill without the two-second throttle. Fully occupied cases start sharing immediately when the batch releases RAM, before the next calculator. Tests also cover context expiry, idle-work shutdown, empty Stanek gifts, error/exit cleanup, and ownership isolation.

`share-handoff.mjs` compares 24 real dispatcher traces against `1ead824` with the same available capacity but share workers occupying reclaimable RAM. Host placement, thread counts and requested delays match, including preparation, chunk fallback, tiny-home emergency reserves and Hacknet fallback. Further cases exercise loss of workers before/during dispatch, failed kills, duplicate/stale/foreign PIDs, old callers and primitive RPC arguments. All **23 current positive suites** pass. The official RAM comparison against `1ead824` shows only the temporary dispatcher increasing, from **4.0 to 4.9 GB**; kernel stays **5.85 GB** and share workers **4.1 GB**. The historical `reproduce.mjs` describes original defects and is not a positive current-branch suite.
